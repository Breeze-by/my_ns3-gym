# ROS 2 P1C 理想通信探索基线阶段报告

日期：2026-09-15

## 1. 结论

P1C 的实验入口、固定任务口径和主要工程门禁已经实现，但退出条件尚未满足，因此状态保持
`进行中`，不能进入 P2。

已确认的正式口径为：`my_world.world`、2 台机器人、共同出生/充电区中心 `(0,0)` 半径
1 m、Gazebo seeds 101/102/103、正确自由空间覆盖率达到 90% 时成功、600 仿真秒超时。

`p1c_ideal_20260914_retry4` 三种子均通过基础设施门禁，但覆盖率仅为 78.6%、75.7%、
76.5%，成功率 0/3。最新候选策略在 seed 101、600 秒得到 78.7% 覆盖、100.571 m 路径、
31 个目标中 25 个成功、5 个取消、0 次碰撞，仍未达到 90%。

## 2. 本轮已实现

- 评估器 schema 升级为 v2：实现 90% 成功/600 秒超时，记录 80%/90%/95% 首达时间、
  每台机器人起终点、任务完成状态和失败原因；
- 两机器人固定出生在 `(0,-0.45)` 与 `(0,0.45)`，均位于确认的起始/充电区；
- 关闭 world 南侧外门，避免机器人离开实验室导致假探索；真值 box 数从 25 变为 26；
- Waffle diff-drive 显式使用 world odometry source，评估起点与 Gazebo 真值一致；
- 新增串行批量入口 `scripts/run_ideal_baseline.py`，每 seed 使用新进程并增量写
  `summary.csv/json`；
- smoke 支持 episode id、覆盖阈值和 goal timeout，并校验 evaluator schema；生命周期门禁
  现在包含 controller、planner 和 bt_navigator；
- Nav2 goal 超过 60 仿真秒会取消，失败/拒绝会释放预留；启动期拒绝不再永久拉黑目标；
- 每台机器人从自己的 `/tbN/map` 选择前沿，避免融合图目标落在本机 global costmap 外；
- 一个前沿组的质心候选无效时会尝试组内其他安全栅格；成功目标保留为访问历史，避免
  A→B→A 重复；
- Nav2 保持 45 秒错峰启动，control/evaluator 延后到最后一套 Nav2 启动 60 秒后加入。

## 3. 正式批次

统一入口：

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
PYTHONNOUSERSITE=1 python3 scripts/run_ideal_baseline.py \
  --seeds 101 102 103 --robot-count 2 \
  --duration 600 --coverage-threshold 0.9 --goal-timeout 60 \
  --run-id p1c_ideal_20260914_retry4
```

结果：

| Seed | 基础设施 | 覆盖率 | 路径 (m) | Goal 成功/总数 | 终止 |
|---:|---|---:|---:|---:|---|
| 101 | PASS | 0.7856 | 63.674 | 2/11 | timeout |
| 102 | PASS | 0.7575 | 60.919 | 3/8 | timeout |
| 103 | PASS | 0.7647 | 32.745 | 2/6 | timeout |

输出：`ros2_ws/ros2-multi-robot-automap/log/ideal_baseline/p1c_ideal_20260914_retry4/`。
该目录被 Git 忽略；汇总内容和结论已同步到 `log.md`。

此前关闭外门后的 `retry2` 为 78.6%、86.8%、78.0%；加入 60 秒 goal timeout 后的
`retry3` 为 83.1%、77.6%、74.1%。这些结果共同表明原策略会长期占用不可达目标，且固定
Gazebo seed 仍不能消除 ROS 调度、SLAM 和 Nav2 的非确定性。

## 4. 关键诊断和修复验证

同一 seed 101 的 180 秒定向测试中：

| 版本 | 覆盖率 | 路径 (m) | Goal 成功/总数 | 结论 |
|---|---:|---:|---:|---|
| 融合图选点、时钟门控后 | 0.7651 | 44.404 | 2/6 | 多个远端目标停滞 |
| 每机器人本地图选点 | 0.8393 | 54.696 | 2/7 | 消除 `off global costmap`，短窗改善 |
| 组内候选回退 | 0.7382 | 39.935 | 5/10 | 目标供给增加，但路径局部化 |
| 严格 lifecycle 门禁 | 0.7258 | 36.376 | 15/17 | 导航成功率高但出现 A↔B 往返 |
| 保留成功目标历史、延迟控制 | 0.7377 | 45.557 | 13/16 | 往返消除，持续访问新目标 |

最终 600 秒命令：

```bash
PYTHONNOUSERSITE=1 python3 scripts/ros_smoke_test.py \
  --robot-count 2 --gazebo-seed 101 --goal-timeout 60 \
  --startup-timeout 300 --shutdown-timeout 60 \
  --evaluation-duration 600 --coverage-threshold 0.9 \
  --evaluation-wait-timeout 1200 \
  --episode-id p1c_visited_history_seed101_600
```

结果：PASS 基础设施，覆盖率 0.7873，路径 100.571 m，25/31 goal 成功，5 个取消，
0 次碰撞，任务 timeout。输出：
`log/evaluation/p1c_visited_history_seed101_600.json`。

## 5. 失败和回退

- 首个批次因 smoke 使用瞬时 node list 判断 evaluator 存活而产生 3 个基础设施假失败，已改为
  从 launch 日志检测 evaluator 进程死亡；
- 机器人曾通过 world 南侧开口离开实验室，已关闭该外门；
- evaluator 在仿真时钟仍为 0 时启动会把 Gazebo 启动时长计入 episode，已增加时钟门控；
- 多轮直接 `navigation_launch.py`/navigation-only 尝试出现参数未加载、lifecycle service
  超时或 action 全部拒绝，均已回退到原 proven bringup；
- 两次 600 秒候选运行因 lifecycle 未就绪而中断/失败，未作为策略样本；smoke 现在检查
  bt_navigator，并且正式结论只使用门禁通过的运行；
- 一次 pytest 收集因未 source `install/setup.bash` 失败，正确环境下随后 4 项测试通过；
- `ros2 action list --no-daemon` 在 Humble 不受支持，且默认 daemon 有残留图缓存，因此未把
  action list 纳入门禁。

所有失败、打断、命令、run-id 和输出路径均在 `log.md` 保留。

## 6. 当前阻塞点与下一轮建议

当前基线能稳定启动、连续产生新目标、避免明显重复，并在 600 秒走过约 100 m，但仍只覆盖
约 79%。日志显示某台机器人在自己的局部 SLAM 前沿耗尽后会空闲，而融合地图仍有其他区域；
直接恢复融合图选点又会重新引入目标超出本机 global costmap 的问题。

下一轮建议实现“受控全局接管”：本地图无候选时，从融合图生成候选，通过对应机器人的
Nav2 `ComputePathToPose` 预检，只有实际 global costmap 能生成路径才提交
`NavigateToPose`；无路径候选立即释放/拉黑，不占用 60 秒。先用 seed 101 的 180 秒定向
测试验证目标供给和越界日志，再跑 101/102/103 正式批次。

该设计会扩大 control 的异步状态机，属于下一轮需要用户确认的工程方向。本报告请求用户
检查：是否接受本轮 P1C 中间成果，并按上述“融合图候选 + Nav2 路径预检”继续，而不是降低
90% 阈值或延长 600 秒超时。

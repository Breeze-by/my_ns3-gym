## 1. 继续工作的依据与边界

V21 的一次原生诊断已结束，不自动重试。固定三机器人、单 worker、两次 open101 完整进程重建，各完成 32 次 API step；64 个动作均提交并返回，policy/GPU/optimizer 为零，`training_eligible=false`。原生采集与关闭成功，但 Cadence 内嵌 Runtime 的真实 guard receipt 因果门失败，**完整诊断 FAIL 保留**，不改写为审计误报或资格通过。

已定位的一条失败记录中，worker 收到并消费 drive ACK 后允许推进，guard 对同一 ACK 的真实订阅回调晚于该许可 1.076029 ms。ACK 最终存在、payload 相符和原生发布记录完整，不能补造 guard 在推进前已经收到的事实。修复应补齐真实执行屏障，不能仅放宽离线比较、用 worker 回执代替 guard 接收，或事后改写 wall 顺序。

两个回合的最终正确自由覆盖率约 74.12% / 73.05%，地图质量与三机参与门均未通过，95% 任务成功均为 false。tb1/tb3 路径分别仅约 .0154/.0071 m 和 .0152/.0911 m；收到目标、导航保持 active 与零接触不能代表充分参与。64 次决策中 35 次只有一个合法动作，不能视为 64 次有选择探索。原生关闭已闭合，也不能证明长期安全停止、长训练稳定性或已学会探索。

原生实际 wait 为 2073.892364923 秒，约 .03086 API step/墙秒。完整主活动与外部收口的实费 union 为 3263.823140435 秒，约 .01961 API step/墙秒；后者是本次短诊断产出率，**不是合格训练吞吐**。这支持先检验更快采样环境的成本与接口是否可用，不支持直接扩大原生 PPO 训练。

V21 详细闭合、原始失败、消费者结果、进程身份及封存入口以本轮主报告和封存索引为准；本文件不替代它们。

## 2. 先完成已有授权内的 CPU 修复准备

本轮已在既有常规修改/修复/验证授权内完成真实 guard receipt barrier 的最小修复与 CPU 反例、回归；系统ROS组合132项通过，实际outer rc0/9.439727408秒，详见 [V21修复与原回执](20261020_mr3_p2a_v21_feasibility.md)。无需再次询问常规修复许可，但尚无修复后native证据。修改保留旧记录和原 FAIL，采用新源码冻结；不得把修复后的 CPU PASS 借给旧原生运行。

必须维持当前 causal obligation：允许下一物理量子推进前，应取得 guard 对本次实际应用 ACK 的真实接收与匹配证据，绑定 episode epoch、robot、clock、命令序号、decision 序号和实际应用目标；陈旧、重复、跨 epoch、错误目标或缺失回执均不得释放屏障。worker 自己收到 ACK、publisher 已发布 ACK 或事后 guard 收到，都不能替代这一义务。

实现复用真实driver的 `mr3-drive-target-consumed-v1` 与guard已有tracker，v2 `MotionControlPhase`在释放现有motion ACK前通过原 `DrivePhaseClient.matching(status)` 检查三个最新实际回执；不新增RPC/schema、sleep、重发或消费tracker历史。真实ingress记录先于tracker回调与poll，第三份匹配ACK回调自然完成现有phase；worker此后才能通过自己的屏障并推进。STOP/takeover零输出立即，完成ACK等待相同真实屏障；legacy、去重/序号回退拒绝、目标匹配与原wall timeout失败规则保持。原reader所有门不改。

CPU 验证已覆盖 worker 先到而 guard 后到、guard 先到、错误/迟到/重复 ACK、跨 epoch、timeout、停止与关闭路径，以及等待过程不会自行推进物理时间。该CPU通过只交付可复核的实现与新冻结准备；不自动启动 native 诊断、完整矩阵、minimum 或 PPO。需要原生确认时，另列具体受影响范围、消费者、预算与退出条件，保留现行完整资格门。

## 3. 二维阶段本次请求接受的范围

本次仅请求接受：**实现一个有限二维代理环境，验证接口符合性，并执行一次零更新容量活动。** 不请求二维预训练、原生迁移、原生微调、策略选型、正式 95% 验收或网络接入。实现与容量成功也不自动授权后续训练。

固定三台 tb1/tb2/tb3，保持联合稳定子目标接口、K=8、KEEP/WAIT、1000 位联合 mask 与现有目标所有权约束。动作来源为事先固定 seed 的合法 mask 均匀随机输入，不创建或调用策略模型，不执行 rollout 学习或 optimizer。每个环境使用独立可重现的随机流，保存完整初始 seed、分流规则、每次实际 mask 与动作；并行调度不能改变其他环境的随机流。

当前输入与编码使用 **`mr3-observation-v3` / `mr3-learning-tensors-v2`**。机器人特征宽度及字段顺序直接取当前 `ROBOT_FIELDS`，其余张量维度、尺度、缺失/valid/越界位直接取现有 encoder 常量；不得沿用 [旧二维选项](20261015_mr3_2d_option.md)中的 v2/v1 schema 或旧机器人 64 维描述。

## 4. 实现与信息边界

- 直接复用已有 `mr3_observation`、学习端 `encode_snapshot`、`GoalDispatcher`、`Envelope/ReceivedStore/IdealTransport`、`ReceivedActivity`、`RewardLedger` 与 episode 规则、reach 几何核。先核对可直接导入的纯函数及其依赖，不为二维复制一套候选、mask、奖励或安全规则。
- `build_snapshot` 必须显式提供实际交付的 `navigation_maps`，保留 `mr3-own-known-shared-unknown-v1` 导航副本与当前 navigation staging-v5；不能退回默认融合图路径。后端只消费已交付记录，导航/局部规划只使用本机图与已交付共享图、队友状态；source/generated/received 时刻、epoch/sequence/version/hash 和陈旧性语义保持。
- 当前 `mr3_information.py` / `merge_map.py` 含 ROS 依赖。优先采用无 ROS 节点的 system Python 后端及现有 IPC，复用同一融合函数和消息结构；不把 ROS `PYTHONPATH` 拼入 conda，也不复制第二套融合规则。若必须提取纯融合核，先做保持行为的单点提取与等价回归，另绑定新冻结，再开展二维活动；不能把该提取当成旧原生资格仍有效。
- 二维局部执行器仅规划并执行输入指定的子目标，在已观测导航栅格上求路并做差速积分。禁止真值最短路、真值可达 mask、真值候选筛选或手工探索目标兜底。完整世界几何只供模拟射线、运动碰撞与隔离评价/奖励；actor 的估计状态由单独模型生成，不读取 evaluator 的真值路径或位姿记录。
- 传感、状态、交付与受控量子的时刻从当前 reach 实际 producer 和契约逐项冻结。旧稿 10 Hz/1 Hz/5 Hz 仅为历史 nominal 参考，不直接冒充当前完整 phase 契约。二维 ACK、接触、定位和动力学均须显式标为代理模型，不伪造 Gazebo/SLAM/Nav2/DDS 或 18 源真实接触收据。

## 5. 先符合性，后容量；保持零更新

先以封存 received-only 快照和有限合成反例验证：相同输入的候选/mask、编码张量与字段含义；目标接受、承诺、KEEP、取消确认、终态和租约；reward 的 dt、首份有效观测/warmup 与 seq0 绑定；reset 后 epoch、缓存、历史、目标、奖励和随机流均正确重置。覆盖未来值、重复、迟到、跨 epoch 与缺失值，不能用后来健康记录覆盖先前坏源。

增加信息隔离检查：只改变尚未可见障碍时，已交付输入相同的 actor/candidate/mask/safety 输出必须不变；只改变隔离 reward truth 时，不得影响观测或动作约束。所用输入、函数源码、配置及输出均绑定 SHA，保留独立核对，不由 producer 自报符合性 PASS。

二维积分先声明 20 ms 和 10 ms 的收敛对照及判断方法，检查路径/停止/碰撞代理差异，不把它称为 Gazebo 1 ms 物理 tick 或 50 Hz 原生时钟证明。deadline 保持 `terminated`，外部采样限保持 `truncated`；任务为 95%/300 秒及原地图质量、参与定义，原生专有门以“未提供”标记，不能填 true。

符合性有未解决失败时，容量活动不得入场；保留失败与有限 CPU 定位结果，提交结论，不自动改 schema、场景、阈值或增加尝试。

## 6. 一次容量候选：9000 ENV.step / 3600 墙秒双重上限

仅在用户接受二维范围、实现与符合性准备完成、源码和配置冻结后，生成精确 sealed plan 并提交推送，再执行以下唯一活动：

| 开发场景 | open、rooms、corridors；全部已见，不称未见测试 |
| 各场景任务 seed | 101、103，共六个 scene/seed 单元 |
| 单环境配置 | 1 env，每 env 依次完成六个单元，共最多 6 episodes |

3600 秒从一次活动的真实 outer 起点计算，包含两组的初始化、启动、reset、全部失败、已提交工作等待、关闭、必要独立审计和外部收口；并行区间按 union 只计一次，nested 不再重复扣费。必须预先为关闭、审计和外部收口划出子预约，禁止将 3600 全用于采集。达到步数或墙时准入边界即停止提交新工作，完成真实关闭；超时尾与异常全额入账，超限保留 FAIL，不能把合作式上限伪称绝对硬中断保证。

本次比较分别报告 1/4 env 的实际分母和含启动/失败/关闭/审计的总分母，不假设并行线性加速。若 9000 步全部取得，3600 秒对应活动平均 2.5 ENV.step/墙秒；若提前终态则报告实际样本与耗时，不虚报已完成 9000 步，也不把短任务速率直接预测为未来训练容量。容量不足、符合性失败或执行错误均触发本次收口，不自动增加时数或原生实验。

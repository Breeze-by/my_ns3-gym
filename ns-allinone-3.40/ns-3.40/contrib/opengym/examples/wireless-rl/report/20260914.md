# ROS 2 P1A 可重复 headless smoke 报告

日期：2026-09-14

## 1. 目的

按照 `RESEARCH_PLAN.md` 月 1–2 的第一项工作，先把现有 ROS 2
Gazebo/SLAM/Nav2/地图合并/探索链路变成有固定 seed、明确 PASS/FAIL 和有界退出的
headless smoke 基础。此步骤是后续真值评估器和任务实验的前置条件。

## 2. 工程改动

- 主 launch 新增 `gazebo_seed`、`spawn_timeout` 和 `auto_save_map` 参数；
- `spawn_entity.py` 默认等待时间由其原生 30 秒改为项目默认 90 秒，降低冷启动误判；
- headquarters 改为原生 ROS launch `Node`，并在自身声明 `robot_count`；
- control 和 merge_map 对 SIGINT/外部 shutdown 做有界清理，避免重复
  `rclpy.shutdown()` 和 smoke 退出时保存地图；
- 新增 `scripts/ros_smoke_test.py`，检查每台机器人核心 topic、Nav2 lifecycle、
  lidar 消息和合并地图消息，并只清理自己启动的进程；
- 新增 `IMPLEMENTATION_PLAN.md`，记录后续工程检查点和用户验收边界。

代码状态：以 commit `d45d88b` 为基线的 P0/P1A 工作树；本报告与代码将在同一提交中保存。

## 4. Smoke 过程和结果

所有运行均先执行：

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
source /usr/share/gazebo/setup.sh
export TURTLEBOT3_MODEL=waffle
```

### 4.1 首次 1 机器人尝试：失败

```bash
python3 scripts/ros_smoke_test.py \
  --robot-count 1 --gazebo-seed 1 \
  --startup-timeout 180 --shutdown-timeout 45
```

结果：FAIL。topic 已出现，但单次 `ros2 lifecycle get` 超过脚本原定 5 秒，脚本过早
终止。原始日志：`log/smoke/robots1_seed1_20260914-172800.log`。结论：判定器需要把
单次查询超时当作“尚未就绪”继续轮询，不能直接判整个 launch 失败。

### 4.2 修正判定器后的 1 机器人运行：通过

同一命令通过，原始日志：`log/smoke/robots1_seed1_20260914-172903.log`。之后把
headquarters 从嵌套 `ros2 run` 改为原生 launch `Node`，再用同一命令复测，最终结果
仍为 PASS。最终原始日志：`log/smoke/robots1_seed1_20260914-173031.log`。

### 4.3 2 机器人运行：通过

```bash
python3 scripts/ros_smoke_test.py \
  --robot-count 2 --gazebo-seed 1 \
  --startup-timeout 240 --shutdown-timeout 60
```

结果：PASS。原始日志：`log/smoke/robots2_seed1_20260914-173107.log`。

### 4.4 3 机器人运行：通过

```bash
python3 scripts/ros_smoke_test.py \
  --robot-count 3 --gazebo-seed 1 \
  --startup-timeout 300 --shutdown-timeout 75
```

结果：PASS。原始日志：`log/smoke/robots3_seed1_20260914-173259.log`。

三次最终 PASS 均满足：

- `/merge_map` 和每台机器人的 `/cmd_vel`、`/map`、`/odom`、`/scan` 已发现；
- 每台机器人的 Nav2 controller 和 planner lifecycle 为 `active`；
- 实际收到至少一条 `tb1` lidar 消息和一条合并地图消息；
- dwell 期间 launch 保持存活；
- SIGINT 后在脚本 shutdown timeout 内退出，未残留 Gazebo/ROS 进程。

## 5. 结论和边界

P1A 的工程退出条件已满足，状态改为“待用户验收”。当前只能说明 1–3 机器人基础栈在
Gazebo seed 1 下能够启动、发布数据并有界退出，不能说明：

- 探索任务已经完成；
- 相同 seed 的完整轨迹逐次完全一致；
- 多个 seeds 下 2 机器人能稳定达到探索退出条件；
- 已有覆盖率、路径、碰撞、任务阶段或失败原因等正式指标；
- ROS 直连旁路已经切断或网络已经影响机器人任务。

这些分别属于 P1B、P1C 和 P3 之后的检查点。下一步在用户验收后进入 P1B：实现独立
真值任务评估器，先固定指标语义和 episode 输出，不改动现有 frontier/Nav2 决策。

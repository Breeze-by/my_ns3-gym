## 目标和边界

P3B 在同一 `GatewayEnvelope` 协议上增加可复现的应用层故障替身，作为进入 ns-3 之前的语义门禁。默认
`gateway_mode:=ideal` 保持 P3A 的零损行为；`gateway_mode:=fault` 才启用故障队列。任务模式统一为
`coverage`、`target` 或 `rally`，由 launch、评估器和 smoke 共同读取。

本阶段不声称已经模拟 Wi-Fi，不测量传播、吞吐、空口 airtime、RTF 或 sim-to-real 差异。

## 实现

- `fault_model.py` 提供上下行独立的固定 seed 传输队列，按消息 attempt 注入延迟和丢包，并支持重复、窗口乱序、TTL 过期、队列溢出和有限重传。
- `ideal_gateway.py` 为消息保留源时间、序号、版本和 correlation id，拒绝过期/旧版本，发布
  `/gateway/message_events`，并可通过 `gateway_ledger_path` 写 JSONL 账本。
- 地图、位姿和 TF 数据过期时，中央协调器暂停新的分配；过期地图不会触发重规划。
- `navigation_gateway.py` 为导航命令提供幂等 command id、deadline、有限重试和超时 abort；机器人本地
  电池状态不是 ACTIVE 时可以直接取消本地 Nav2 action。
- `mission_mode` 统一评估器终止条件，未交付的目标检测不会进入 `RALLY`。

每条 attempt 的账本字段包括 `source_time`、`enqueue_time`、`admit_time`、`tx_time`、
`delivery_time` 或 `drop_time`、`message_id`、序号、版本、correlation id、attempt 次数和原因。

## ROS fault-mode 保留样本

2026-09-25 曾运行两机器人 `my_world.world`、Gazebo seed 101、`mission_mode=rally` 的 100% 上行丢包
smoke：上行/下行丢包率为 `1.0/0.0`，最大重试 2 次，评估上限 90 秒。Nav2 readiness 和 P3A
forbidden-bypass audit 通过；启动后所有地图、位姿和 TF 上行消息均被丢弃，中央没有收到 `/merge_map`，
没有导航目标，也没有进入 `RALLY`。评估结果为 `success=false`、`failure_reason=no_data`、
`map_message_count=0`、`nav_goal_count=0`。

这是符合安全预期的 post-start 失败样本：检测未交付时不能进入 `RALLY`。它发生在随后 ACK、源时间和
本地 deadline 语义收紧之前，因此不能作为硬化后完整任务矩阵的替代证据，也不能被解释为故障网络成功率。

## 原 P3B 计划中的后续项（现归入 P3B.5/P3C/P4A）

1. P3B.5：还没有在硬化后的当前 HEAD 上完成覆盖 `coverage/target/rally`、多 world、多 seed、
   延迟/丢包组合的 Gazebo fault-mode 任务矩阵。
2. P3B.5：还没有故障条件下的 `COMPLETE`/`PARTIAL_COMPLETE` 比例、完成时间、碰撞、电量和
   freshness/本地保持统计，因此不能与 P2D/P3A ideal 结果做性能比较。
3. P3C：还没有默认打开的 gateway 实时面板、通信曲线、CSV/JSON 指标守恒和 ideal/fault 叠加报告。
4. P4A：还没有 ns-3 bridge、逐包生成/发送/交付/丢弃字节对账、时间同步、wall time/RTF 和资源记录。
5. P3B.5：文档约定 `gateway_queue_capacity=0` 表示不限制队列，但实现语义需要在故障任务矩阵前统一，
   并把 overflow case 固定进 manifest。

因此当前准确表述是：**P3B 已按应用层故障替身和协议门禁范围验收；P3B.5 继续完成故障条件下的
完整任务闭环，P3C 建立 gateway 通信指标与可视化，真实 ns-3 集成仍属于 P4A。**

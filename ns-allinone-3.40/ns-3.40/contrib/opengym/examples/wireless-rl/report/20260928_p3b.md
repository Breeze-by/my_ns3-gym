# P3B 固定 delay/loss 网络替身

日期：2026-09-28。本报告把 P3B 的实现边界、协议门禁、保留失败和未完成的验收条件集中记录下来。

## 结论

P3B 的确定性应用层故障传输已经实现，协议级 fault matrix 已通过；P3B 整体仍为“待用户验收”。
当前结果证明消息故障语义和安全降级路径，不证明 Gazebo 任务在故障网络下的成功率、完成时间或 Wi-Fi
性能。P4A 的 ns-3 数据包/时间桥接尚未开始。

实现位于提交 `88f6a49`；本次复核使用代码 HEAD `39c788b`，复核开始前工作树干净。

## 目标和边界

P3B 在同一 `GatewayEnvelope` 协议上增加可复现的应用层故障替身，作为进入 ns-3 之前的语义门禁。默认
`gateway_mode:=ideal` 保持 P3A 的零损行为；`gateway_mode:=fault` 才启用故障队列。任务模式统一为
`coverage`、`target` 或 `rally`，由 launch、评估器和 smoke 共同读取。

本阶段不声称已经模拟 Wi-Fi，不测量传播、吞吐、空口 airtime、RTF 或 sim-to-real 差异。

## 实现

- `fault_model.py` 提供上下行独立的固定 seed 传输队列，按消息 attempt 注入延迟和丢包，并支持重复、窗口乱序、TTL 过期、队列溢出和有限重传。
- `ideal_gateway.py` 为消息保留源时间、序号、版本和 correlation id，拒绝过期/旧版本，发布
  `/gateway/message_events`，并可通过 `gateway_ledger_path` 写 JSONL 账本。
- 地图、位姿和 TF 数据过期时，中央协调器暂停新的分配；过期地图不会触发重规划。
- `navigation_gateway.py` 为导航命令提供幂等 command id、deadline、有限重试和超时 abort；机器人本地
  电池状态不是 ACTIVE 时可以直接取消本地 Nav2 action。
- `mission_mode` 统一评估器终止条件，未交付的目标检测不会进入 `RALLY`。

每条 attempt 的账本字段包括 `source_time`、`enqueue_time`、`admit_time`、`tx_time`、
`delivery_time` 或 `drop_time`、`message_id`、序号、版本、correlation id、attempt 次数和原因。

## 协议门禁验证

验证使用 system Python；ROS 2 工程不混入 ns3gym conda Python。

```bash
export PYTHONPATH=/home/zhuyulab/ns3-workspace/ros2_ws/ros2-multi-robot-automap/src/multi_robot_exploration
/usr/bin/python3 -m pytest -q \
  ros2_ws/ros2-multi-robot-automap/src/multi_robot_exploration/test/test_fault_model.py
/usr/bin/python3 ros2_ws/ros2-multi-robot-automap/scripts/run_p3b_fault_matrix.py \
  --output /tmp/p3b_fault_matrix_current.json
```

2026-09-28 复核结果：单测 `4 passed`；矩阵 `status=PASS`。矩阵共有 54 格，即固定 seeds
`101/202/303`、上行/下行两个方向、`0/0.1/1.0` 三种丢包率和 `0/0.5/2.0` 三种延迟。独立检查还确认
TTL 延迟消息记为 `expired_in_flight`，乱序输出为 `[2, 1]`，100% 丢包没有交付。

该矩阵脚本另外验证了有限重传和 TTL/乱序语义；队列溢出有独立单测覆盖。它还没有把队列容量、TTL、
deadline 和重试组合扩展成每个固定 seed 的完整任务矩阵，因此不能单凭此结果关闭 P3B 验收条件。

## ROS fault-mode 保留样本

2026-09-25 曾运行两机器人 `my_world.world`、Gazebo seed 101、`mission_mode=rally` 的 100% 上行丢包
smoke：上行/下行丢包率为 `1.0/0.0`，最大重试 2 次，评估上限 90 秒。Nav2 readiness 和 P3A
forbidden-bypass audit 通过；启动后所有地图、位姿和 TF 上行消息均被丢弃，中央没有收到 `/merge_map`，
没有导航目标，也没有进入 `RALLY`。评估结果为 `success=false`、`failure_reason=no_data`、
`map_message_count=0`、`nav_goal_count=0`。

这是符合安全预期的 post-start 失败样本：检测未交付时不能进入 `RALLY`。它发生在随后 ACK、源时间和
本地 deadline 语义收紧之前，因此不能作为硬化后完整任务矩阵的替代证据，也不能被解释为故障网络成功率。
episode、launch log 和逐消息账本保留在：

```text
ros2_ws/ros2-multi-robot-automap/log/p3b_fault_100up_seed101/
ros2_ws/ros2-multi-robot-automap/log/p3b_fault_100up_seed101.jsonl
```

## 未完成项和验收边界

1. 还没有在硬化后的当前 HEAD 上完成覆盖 `coverage/target/rally`、多 world、多 seed、延迟/丢包组合的
   Gazebo fault-mode 任务矩阵。
2. 还没有故障条件下的 `COMPLETE` 成功率、完成时间、碰撞和充电统计，因此不能与 P2D/P3A ideal
   结果做性能比较。
3. 还没有 P4A 的 ns-3 bridge、逐包生成/发送/交付/丢弃字节对账、时间同步、wall time/RTF 和资源记录。
4. 文档约定 `gateway_queue_capacity=0` 表示不限制队列，但 `ideal_gateway` 当前将 0 转换为 4096；
   正式验收前需要统一实现和文档语义。

因此当前准确表述是：**P3B 应用层故障替身和协议门禁已完成，P3B 阶段整体尚未验收；Gazebo 故障任务
矩阵和 ns-3 集成仍是后续工作。**

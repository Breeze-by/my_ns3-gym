# P3B.5 故障任务闭环与安全降级计划

日期：2026-09-28
状态：进行中（2026-10-01：P3A.6 已由用户验收，任务/时序修复候选正在重验证）
前置验收：P3A、P3A.5 已由用户验收；P3B 的固定应用层故障替身和协议门禁已由用户验收。

## 1. 为什么从 P3B 拆出 P3B.5

P3B 已经证明 gateway 能按固定 seed 注入延迟、丢包、重复、乱序、TTL 过期和有限重传，也能
留下逐次 attempt ledger。但这只回答“消息层是否按规则工作”，没有回答“消息故障会怎样改变
完整机器人任务”。因此，P3B 的任务层剩余内容不再笼统写成“P3B 未完成”，统一标记为 P3B.5。

P3B.5 仍使用同一个应用层 fault gateway，不接真实 ns-3 Wi-Fi；真实 Wi-Fi 数据包、空口竞争、
传播、时间桥接属于后续 P4A/P4B。

## 2. P3B.5 要回答的问题

1. 丢包、延迟、过期和队列拥塞是否会让探索、目标确认、地图融合、集合和充电出现可解释退化？
2. 理想通信与故障通信相比，任务完成率、完成时间、覆盖率、碰撞、电量和集合质量差多少？
3. 哪类消息最先成为瓶颈：地图、位姿/TF、目标检测、电池状态还是导航命令？
4. 机器人和中央协调器在没有新鲜消息时是否执行了明确的保障性动作，而不是继续盲目使用旧状态？
5. 单机器人故障后，健康机器人是否继续工作，剩余机器人集合是否正确进入 `PARTIAL_COMPLETE`？

## 3. 固定实验矩阵

建立不可随意修改的 `p3b5_fault_manifest`。每个 case 必须写入：代码 commit、world、目标位置、
机器人数量、能量配置、mission mode、Gazebo seed、fault seed、上下行参数、TTL、deadline、
最大重试、队列容量、episode horizon、ROS/Gazebo 版本和配置哈希。

每个故障 case 必须有相同 world、目标、机器人数量、能量、seed 和 horizon 的
`gateway_mode=ideal` 配对对照。理想对照与故障运行必须使用同一个 task stack 和同一份评估器。

最低覆盖：

| 维度 | 固定内容 |
|---|---|
| 任务模式 | `coverage`、`target`、`rally` |
| 场景 | `my_world.world`、rooms、corridors、至少一个未用于调参的 holdout world |
| 机器人 | 2、3 台 |
| 丢包 | 上行/下行独立 0%、10%、100%；另有 burst/连续丢包 case |
| 延迟 | 0、0.5、2 秒；另有超过 TTL 的延迟 case |
| 协议故障 | duplicate、reorder、TTL expired、deadline、retry exhausted、queue overflow |
| 消息类别 | map/map increment、odom/TF、battery、target observation/detection、task state、Nav2 command |
| 结果 | `COMPLETE`、`PARTIAL_COMPLETE`、`FAILED`、timeout、no_data、stale_state、navigation deadline、collision、battery failure |

开发/集成 seed `101/202/303` 只能用于门禁和调试；正式 P3B.5 报告还要另设未调参的 fault seed
和 holdout 组合，不能只挑最容易完成的 case。

## 4. 机器人保障性行为契约

这些行为是安全底线，不是通信策略优化对象，也不能被后续 RL 覆盖：

- **地图、位姿、TF 过期**：中央暂停新的探索分配和基于旧地图的重规划。机器人可以完成当前
  仍安全、仍在 deadline 内的本地目标；目标完成、超时或安全条件失效后，进入停止/等待，直到
  新鲜状态恢复。
- **目标检测未交付**：中央不能进入 `RALLY`，不能用 Gazebo truth 或旧检测伪造目标确认。
- **RALLY 时效**：本轮目标为静态固定目标，新集合决策仍须持有源时间不超过60秒的真实交付确认。
  确认过期后保留任务阶段，停止基于旧目标坐标的新集合动作；已接受命令仍受原deadline和本地安全约束。
  当前地图、位姿、TF、电池新鲜时，允许通过同一gateway在实际当前位置四向扫描，或按当前地图前沿继续搜索；
  无可行前沿时在已知自由、可达区域中搜索未访问邻域，到实际搜索航点后重新扫描。
  搜索候选不使用过期目标坐标，只有重新交付并消费的真实检测才能续租；本地返航和安全避让保持独立。
- **导航命令过期/未确认**：本地 gateway 按 command id 去重，超过 deadline 取消 Nav2 并输出
  明确的 `navigation_deadline` 或 `stale_command` 结果，不能无限保持旧命令。
- **电池和碰撞安全**：本地低电量返航、充电、急停和避障优先于网络；网络断开不能阻止安全返航。
- **恢复**：新鲜消息恢复后，按版本、任务阶段和 command id 恢复；旧消息不得回滚地图、位置或任务状态。
- **单机故障**：中央隔离故障机器人，健康机器人继续执行；剩余机器人集合稳定后发布
  `PARTIAL_COMPLETE`，只有无故障全员集合才发布 `COMPLETE`。

## 6. 退出条件

P3B.5 通过必须同时满足：

1. manifest、命令、commit/config/environment 信息完整，ideal/fault 配对关系可复现；
2. 三种 mission mode、多 world/seed 和所有最低 fault 维度均实际运行，失败样本不覆盖；
3. 每个 case 都有任务结果和 gateway ledger，能解释是网络故障、导航故障、电池故障还是基础设施故障；
4. 100% 丢包和过期消息不会伪造 `RALLY`，stale-state 不会触发危险的新分配；
5. 单机器人故障不会拖停健康机器人；剩余集合正确输出 `PARTIAL_COMPLETE`；
6. 报告至少给出 ideal→fault 的成功率、部分完成率、失败原因分布、RMST/完成时间、AoI/时延、
   PDR/丢包和电量/碰撞变化，并给出 `TDI` 及其置信区间，指出退化首先发生在哪类消息；
7. 不把 P3B.5 结果写成真实 Wi-Fi 性能或 ns-3 闭环结果。

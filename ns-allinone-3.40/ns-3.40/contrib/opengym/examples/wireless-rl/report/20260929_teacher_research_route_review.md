## 1. 审查结论

当前项目的问题框架是合理且可落地的，但现有表述过宽，容易把已有工作的组成部分误说成创新。
“多机器人 + 真实 Wi-Fi + 真实机器人”本身不构成创新；“任务导向通信”“选择发送者和时机”
“异构机器人”“实物演示”也分别已有直接或高度相关先例。

建议保留以下工程方向：

- 保留多机器人协同探索、目标搜索、充电和集合任务作为任务闭环；
- 保留中央协调器和显式 gateway；
- 第一版不强行改成 MARL，也不在每台机器人上新增一个学习网络；
- 保持 SLAM、Nav2、frontier、目标检测和本地电池安全逻辑固定，把通信准入作为主要研究变量；
- 先测量真实候选消息负载和网络瓶颈，再决定 RL 是否有足够研究空间；
- 以“消息成功且及时送达后是否改变任务决策”为价值核心，而不是只按发送者、消息年龄或 RSSI 排序；
- 用强非学习基线和学习式评分基线先建立困难，再判断 RL 是否真的有必要。

建议暂定的论文问题是：

> 在中央端只掌握有限、滞后且可能过期的机器人信息，应用消息类型具有不同任务价值，底层 Wi-Fi
> 仍负责竞争、排队和重传的条件下，如何在发送前调度消息准入，使协同搜索任务在完成时间、成功率、
> 信息新鲜度和通信代价之间取得更好的权衡？

这里的“通信调度”首先指应用层消息准入，不等同于取代 802.11 DCF/EDCA、MAC 重传、MCS 或功率控制。

## 3. 问题层次和本项目边界

老师意见把“通信协议”拆成三个层次。当前项目应明确只把第二层的一部分作为第一版学习变量，
并把三层的接口都记录下来。

### 3.1 消息内容生成

机器人根据本地 SLAM、位姿、电量、任务状态和检测器产生地图增量、frontier 摘要、目标检测、
心跳和状态消息。第一版固定消息语义、序列化和摘要规则，不学习新的端到端 embedding，也不把
消息内容变成不可解释的连续向量。

这并不声称消息编码没有研究价值；它只表示本项目先隔离“消息内容”变量，以便把收益归因到准入
调度。如果将来要学习压缩或内容生成，必须作为单独消融，不得与准入策略混在主比较中。

### 3.2 应用层消息准入调度

中央策略在每个决策窗选择：

```text
action = (endpoint, message_type)
```

并保留“不准入普通消息”的动作。动作作用在消息进入发送队列之前，因此通信账本可以区分：

```text
generated -> requested/candidate -> admitted -> enqueued -> transmitted -> delivered/expired/dropped
```

关键事件、心跳、低电量返航、急停和导航安全命令不能被策略永久压制；它们应有最大等待时间、
固定重试或本地安全降级。普通地图和状态消息可以被准入策略延迟、替代或丢弃。

### 3.3 Wi-Fi 实际交付

应用层准入不会决定某个时刻一定获得无线介质。进入 ns-3 后，DCF/EDCA、队列、竞争、帧交换、
ACK、重传、传播和干扰仍然决定实际交付。论文必须分别报告：

- 消息是否被策略准入；
- 是否进入底层发送队列；
- 是否获得发送机会；
- 是否成功交付、重传、过期或丢弃；
- 接收端是否消费了该消息并改变任务决策。

不能把“中央允许发送”写成“消息已经发送”，也不能把应用层准入写成 MAC 调度。

### 3.4 单智能体集中式 RL，而非默认 MARL

如果只有中央控制器执行学习策略，多个机器人只是环境中的多个 endpoint，这个问题可以定义为：

```text
一个集中式、部分可观测的单智能体通信调度问题
```

中央端的观测是最后收到的位姿、电量、地图版本、候选摘要、AoI、队列和链路统计，而不是 Gazebo
当前真值。训练时可以使用 centralized critic 或完整状态做辅助，但执行策略必须只使用可部署
观测。

只有当每台机器人独立运行需要学习的通信或行动策略，且这些策略通过团队交互共同学习时，才将
方法组织为 MARL。网络有多个输出头、系统有多台机器人、训练集中式或分布式，都不足以单独决定
它是 MARL。

## 4. 当前架构中必须补上的信息机制

中央端在没有收到新消息前，不能知道机器人刚刚发现了关键通道。因此“所有信息必须先获中央许可”
会形成自我阻塞。建议把候选产生和准入控制设计为两级机制：

1. 机器人本地生成低开销候选摘要或发送请求，例如消息类型、版本、大小、生成时间、局部信息增益、
   任务阶段和紧急等级；
2. 中央端根据已经收到的摘要和历史交付信息下发短期准入许可或预算；
3. 机器人只有获得许可后才把对应大消息放入发送队列；
4. 心跳、低电量、确认目标、急停和返航请求保留最低限度的独立通告路径；
5. 摘要、许可、反馈和重试本身也计入字节、排队、时延和失败账本。

最低机制应包括：

| 机制 | 目的 | 约束 |
|---|---|---|
| heartbeat | 让中央知道机器人仍在线 | 小、周期、允许旧包丢失 |
| candidate/request | 暴露“可能值得发送”的消息 | 不能携带不可部署的全局真值 |
| admission grant | 控制普通大消息进入网络 | 有有效期，不能撤回已经进入 MAC 队列的包 |
| critical event | 防止中央因未知事件而永远不给许可 | 固定最大等待和重试；断网时不保证送达 |
| delivery feedback | 更新中央端对实际交付的认识 | 记录 ACK、重传和消费时刻 |

这项机制是当前计划中最需要新增的协议设计点。它比简单增加 RSSI、电量或机器人数量更可能
形成可验证的研究问题。

## 5. 候选创新假设

目前不能宣布已经存在文献空白，只能先提出可证伪的候选假设：

> 当机器人消息的任务价值随地图、frontier、目标状态和信息新鲜度动态变化，且无线交付存在排队、
> 时延和竞争时，仅按发送者优先级、固定周期、消息年龄或链路质量的策略，会在“高链路质量但低决策
> 价值”和“低链路质量但可能改变任务分配”的消息之间做出系统性错误取舍；使用接收端实际可见的
> 任务状态、候选摘要、AoI、交付概率和队列代价进行时序调度，可能改善任务—通信 Pareto 权衡。

该假设只有在下列证据同时成立时才有论文价值：

1. 合理负载下网络确实存在消息排队、过期或竞争造成的任务影响，或者节省通信不会降低任务性能；
2. 强非学习基线在某一类可复现条件下出现明确且可解释的失效；
3. 新机制针对该失效，而不是只增加输入特征或训练时间；
4. 所有策略使用相同的机器人任务算法、消息语义、可获得观测、网络条件和安全约束；
5. 收益沿着 `准入 -> 交付 -> 接收状态 -> 任务决策 -> 机器人行为 -> 任务指标` 传递；
6. 收益能在未用于调参的 world、目标、干扰和实物场景中复现；
7. 如果强贪心已达到同等效果，则如实把结论改成“不需要复杂 RL”或“RL 没有显著优势”。

## 6. 建议增加的强基线

所有基线都应使用相同的机器人和网络栈，并将候选摘要、许可、心跳和控制开销计入通信量。
至少应包括：

| 基线 | 控制规则 | 用途 |
|---|---|---|
| no communication | 普通跨端消息全部不交付，保留本地安全和关键事件规则 | 任务下界 |
| always send | 候选生成后全部进入发送通道 | 通信上界和拥塞压力 |
| fixed-period | 各消息类型固定周期发送 | 工程常见基线 |
| event-triggered | 地图变化、位姿变化或检测事件超过阈值才请求 | 低复杂度压缩基线 |
| freshness/deadline | 按 AoI、TTL、截止时间排序 | 时效基线 |
| task-priority | 目标、低电量和任务命令优先于普通状态/地图 | 任务规则基线 |
| task-value greedy | 预计任务收益、及时交付概率和通信代价加权排序 | 最重要的非学习基线 |
| link-aware greedy | 在任务价值相近时结合 RSSI/PDR/队列选择 | 网络感知基线 |
| SchedNet-inspired | 在相同观测和实际候选队列上适配学习式优先级 | 最接近的学习式强基线 |
| centralized RL | 本项目候选的集中式单智能体策略 | 主方法候选 |

“task-value greedy”不能被省略。它用于判断问题是否真的需要长期学习，而不是把规则方法故意
做弱后再展示 RL 优势。

## 7. 必须先做的三项测量和验证

### 7.1 真实消息负载测量

在接入 ns-3 和训练前，先在当前 Gazebo/gateway task stack 上测量：

- 各消息类型的生成频率、payload 大小和压缩前后大小；
- 2/3 台机器人在 lab、rooms、corridors 中的候选数量；
- 地图更新 burst、状态心跳和检测事件的时间分布；
- ideal gateway 下的应用 offered load、实际队列深度和消息 AoI；
- 相同负载下无干扰 Wi-Fi、合理背景流和受干扰 Wi-Fi 的 PDR、airtime、排队和端到端时延；
- 通信开销相对于移动/空闲能耗是否真的不可忽略。

如果合理负载下网络不是瓶颈，应研究“在不降低任务表现的前提下节省通信”，不能人为注入没有应用依据
的拥塞来制造 RL 优势。

### 7.2 挑战强基线

在相同任务算法、候选接口、观测范围、网络、seed 和 episode horizon 下运行上一节基线。每个失败、
超时和基础设施失败都保留；不能只统计成功任务的完成时间。

### 7.3 任务闭环因果追踪

至少保留一类可逐消息回放的因果链：

```text
candidate/request
  -> admission decision
  -> queue/airtime/retry
  -> delivered or expired
  -> received map/state version
  -> frontier/task allocation
  -> robot path and motion
  -> coverage, target time, completion, energy
```

账本必须同时有 `source_time`、`enqueue_time`、`admit_time`、`tx_time`、`delivery_time`、
`consume_time`、`drop_time`、`message_id`、版本、方向、发送者、接收者和尝试次数。任务结果必须
和 payload、airtime、端到端时延、AoI、过期信息一起报告。

## 9. 对 `IMPLEMENTATION_PLAN.md` 的待审核修改建议

这些建议应作为新的检查点或现有检查点退出条件的补充，不能直接跳过当前 P3B.5/P3C 边界。

### 9.1 在进入 ns-3 前增加“负载与调度空间审计”门

建议新增 `P3C.5` 或在 P4A-0 前加入独立门，暂名：

```text
P3C.5：应用候选负载、候选摘要和任务价值测量
```

最短退出条件：

- 固定至少 2/3 机器人、lab/rooms/corridors 和 holdout world；
- 测量每种消息的生成、摘要、准入、payload、字节、队列和 AoI；
- 实际加入 candidate/request/grant/heartbeat/critical-event 账本；
- 证明至少一种合理网络条件下存在排队/过期影响，或证明节省通信而任务不退化；
- 输出 `traffic_manifest`、消息 schema hash、时间基准和原始 JSONL；
- 若网络不是瓶颈，记录负结果并重定研究问题，不进入“人为拥塞”的 RL 训练。

### 9.2 重新冻结当前 task stack

2026-09-29 的控制器和电池返航优化发生在已有 P3A.5 历史冻结之后。建议在计划中增加：

```text
P3A.6：当前 HEAD task-stack re-freeze
```

退出条件：

- 当前 HEAD 重新通过 P2D 完整理想通信矩阵；
- 重新通过 P3A forbidden-bypass、协议和 gateway 审计；
- 重新运行必要的强制充电和多机器人联合探索回归；
- 写入新的 `task_stack_frozen_commit`、环境、配置和消息 schema manifest；
- 在此门通过前，当前 HEAD 只能作为 exploratory task-stack，不能作为网络/RL 公平基线。

### 9.3 在 P4A-0 中显式加入应用层准入

P4A-0 不应只对账已有 gateway 到 ns-3 的字节，还应区分：

```text
generated/candidate -> admitted -> enqueue -> tx -> delivery -> consume
```

退出条件应包括：

- 准入前消息不会进入网络队列；
- 被拒绝、过期、替代和重试分别记账；
- 关键消息的最大等待和本地安全降级可测试；
- 中央端执行观测只来自收到的摘要和反馈，不读取机器人隐藏候选队列；
- 应用层账本和 ns-3 逐包字节严格守恒。

### 9.4 将 P5 改为“先基线、后 RL”

建议 P5 分为：

1. P5A：固定候选消息和强非学习基线；
2. P5B：SchedNet-inspired 学习式评分适配；
3. P5C：集中式单智能体 RL；
4. P5D：只有在需要时才做 shared actor/MARL 扩展。

每一步都必须使用相同任务算法和网络条件。P5C 的退出条件不应是“DQN 训练收敛”，而应是：

- RL 至少在一个预注册的、强贪心明确失败的条件下有可重复收益；
- 收益不是只来自更多通信或更多训练预算；
- 任务安全和充电不退化；
- held-out 场景上报告配对统计，不挑选成功 seed；
- 如果强贪心相当，则记录“不需要 RL”的结果。

### 9.5 增加因果闭环和负结果退出条件

每个网络策略 episode 都应输出通信、接收状态、任务分配、轨迹和最终任务指标的时间对齐记录。
如果只能证明 PDR 变好而无法证明任务行为变化，不能宣称任务导向通信有效；如果任务完全不受网络
影响，不能通过增加没有依据的流量来修正结果。

## 10. 实验公平性和统计规则建议

### 10.1 固定变量

策略比较时固定：

- Gazebo world、目标位置、出生点、机器人数量和电池配置；
- SLAM、frontier、Nav2、目标检测、充电和故障安全逻辑；
- 消息类型、序列化、摘要算法、候选生成频率和关键消息规则；
- ns-3 AP/STA、信道、MCS、传播、墙损耗、背景流和队列参数；
- 决策窗、episode horizon、seed、训练/validation/test 划分。

策略唯一改变的内容应是普通应用消息的准入和调度；若某基线必须改变消息编码或网络协议，
必须单独标注为“系统适配比较”，不能直接作为公平算法比较。

### 10.2 必须报告的指标

任务侧：完整成功率、`PARTIAL_COMPLETE`、失败原因、完成时间、RMST、目标发现时间、覆盖率、
地图准确率、路径长度、必要/非必要重复覆盖、碰撞、最低电量和充电次数。

通信侧：生成/候选/准入/发送/交付字节、airtime、PDR、排队时延、传输时延、端到端时延、
重传、丢包、过期、队列深度、AoI、fresh-state ratio、控制开销和 CPU/RAM。

因果侧：消息交付后接收地图/状态版本、frontier 数量变化、中央分配变化、机器人目标变化、
轨迹变化和最终任务结果。至少应能回放代表性成功、失败和退化 episode。

### 10.3 统计规则

- 训练、validation、held-out test 场景和 seed 不重叠；
- 所有策略使用配对 episode；
- 保留 pre-start `infrastructure_failure` 和 post-start task failure；
- 先报告 success rate 和区间，再比较 RMST、通信代价和 AoI；
- 不能只保留完成任务的样本；
- 至少 20 个配对 held-out episode 才能支持主要策略比较；
- RL 的优越性是实验结论，不是工程退出条件。

## 11. 论文方向建议

当前最自然的主线是网络化机器人/多机器人系统：通信机制是否让真实机器人团队在不可靠信息
条件下更快、更可靠地完成搜索和建图。网络系统或无线通信投稿也可保留，但需要相应增强协议、
排队、airtime、可复现性和真实网络实验。

暂不建议把论文标题或摘要写成“提出一种新的 MARL 通信协议”。更稳妥的暂定标题是：

```text
面向多机器人协同搜索的任务与网络状态感知应用消息调度及实物验证
```

该标题仍是工作假设，不是最终投稿标题。最终分类取决于哪条证据最强：

- 机器人方向：任务困难、机器人行为变化、真实部署和安全性最强；
- 网络方向：消息准入、排队管理、协议开销和真实 UDP/Wi-Fi 证据最强；
- 无线方向：无线状态、任务价值和资源调度之间的耦合最强；
- 机器学习方向：方法或认识能够推广到多个场景，而不只是 DQN 在当前平台上跑通。

## 12. 暂不建议的工作

在本审查获得审核前，暂不做以下扩展：

- 不为了贴近 MARL 文献给每台机器人新增一个学习通信网络；
- 不同时学习消息内容、导航、SLAM、压缩率、MCS、发射功率和 MAC 参数；
- 不在合理负载测量前人为加入拥塞；
- 不把 RSSI、电量、机器人数量或真实 Wi-Fi 作为单独创新点；
- 不跳过强贪心和 SchedNet-inspired 基线直接训练 RL；
- 不把 ideal gateway、Gazebo 真值或 toy MDP 结果写成 Wi-Fi RL 证据；
- 不把当前 2026-09-29 的 task-stack 工程优化未经重新冻结就替换已有网络基线。

日期：2026-09-28
状态：待开始

## 1. 目标

当前 gateway 的消息在系统中实际流动，但运行者只能从零散日志推断通信是否变差。P3C 要让这条
通信链可见：默认 GUI 运行时打开监控面板，headless 和批量运行也默认写出同一套结构化指标，
从而能直接回答：

- 当前上行/下行数据率是多少？
- 哪类消息在丢包、排队或重试？
- 端到端延迟和 p95 什么时候超过 TTL/deadline？
- AoI/freshness 何时恶化？
- 任务从 `COMPLETE` 退化到 `PARTIAL_COMPLETE` 或 `FAILED` 的时间点是什么？
- 理想通信和故障通信的差异来自哪类消息？

## 2. 可视化边界

P3C 只读 gateway ledger、接收状态存储和任务评估器输出，不发布任务、导航、电池或速度命令。
它不能为了画出曲线而改变消息频率、队列、重试或任务终止条件。所有曲线使用仿真时间，不能使用
GUI 刷新时间代替通信时间。

默认输出：

- GUI：实时面板和四组滚动曲线；
- headless：逐时间窗 CSV、episode JSON 汇总、故障事件 JSONL，必要时保存 PNG/SVG；
- 每个点带 episode、sim_time、direction、message_type、sender、recipient、seed、mission_mode、
  gateway mode 和 fault configuration。

## 3. 指标定义

### 3.1 负载、交付和故障

- generated/admitted/attempted/delivered messages 与 bytes；
- offered throughput、delivered goodput、PDR、loss rate、retry rate；
- TTL expired、queue overflow、duplicate、reorder、retry exhausted；
- queue depth、队列利用率、各消息类别的字节占比。

### 3.2 时延与信息新鲜度

- queue wait、admit→tx、tx→delivery、source→delivery 延迟；
- mean、p50、p95、p99、max，按方向和消息类别拆分；
- AoI mean/p95/max；`AoI(t)=t-source_time(latest_delivered)`；
- fresh-state ratio、stale-state duration、恢复新鲜状态所需时间；
- 检测 `local_confirm→delivered→consumed`、导航命令 deadline success/abort、任务状态传播时间。

### 3.3 任务联动

同一时间轴叠加任务阶段和机器人安全事件：`EXPLORE`、`FOUND`、`RALLY`、`COMPLETE`、
`PARTIAL_COMPLETE`、`FAILED`，以及目标发现、返航、充电、stale-state、导航 deadline、单机故障、
碰撞和恢复事件。

任务侧同时展示 ideal/fault 的 success rate、partial completion rate、失败原因、RMST/完成时间、
目标发现/通知/RALLY 时间、覆盖率、路径、电量和碰撞，并显示 P3B.5 冻结的
`task_degradation_index (TDI)`。TDI 只在 ideal 配对为 `COMPLETE` 时统计：fault 为
`COMPLETE` 记 0，`PARTIAL_COMPLETE` 按未完成的要求参与机器人比例计分，失败/超时记 1。
P3C 只展示和统计，不改变 P3B.5 的任务结果。

## 4. 面板最小布局

1. **通信总览**：上下行 throughput/goodput、PDR、loss/retry、当前 queue depth；
2. **延迟与 AoI**：source→delivery p95、各消息类别 AoI、freshness 阈值线；
3. **消息类别堆叠**：地图、位姿/TF、电池、检测、任务状态、导航命令的字节和交付率；
4. **任务时间轴**：任务阶段、机器人位置/速度摘要、充电/故障/等待事件和通信曲线对齐；
5. **对比模式**：同 seed 的 ideal 与 fault 曲线叠加，显示参数、seed 和 episode id。

默认面板必须能从曲线看出通信是否成为瓶颈，但不能把“曲线好看”当成验收证据。

## 5. 数据守恒与验收

P3C 通过条件：

1. 每个 direction/message_type 的 generated→admitted→attempted→delivered/dropped/expired 字节和
   消息数可对账；重试 attempt 与 logical message 分开统计；
2. CSV/JSON 与 GUI 使用相同的 metrics source；关闭 GUI 后数值不变；
3. 使用仿真时间，ideal/fault 同 seed 可以叠加；p95 在样本不足时明确标记，不填充假值；
4. 可从 ledger 定位首个丢包、首个 TTL 超时、首个 freshness violation 和任务终态变化；
5. 可视化进程不发布控制消息、不改变任务状态、不订阅 Gazebo truth 参与决策；
6. 至少用 P3B.5 的理想、10% 丢包、100% 丢包、TTL 超时和 queue overflow case 展示退化曲线，
   并能解释哪些消息先受影响以及机器人采取了什么保障性动作。

被误写成 Wi-Fi PHY/MAC 性能，也不能代替 P4A 的 packet/clock ledger。
